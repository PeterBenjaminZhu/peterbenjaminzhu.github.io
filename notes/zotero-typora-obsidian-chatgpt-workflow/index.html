Zotero、Typora、Obsidian 与 ChatGPT 的个人科研工作流

2026年11月12日·3 分钟·

文稿目的
#

本文整理一套面向中长期研究项目的个人工作流：以 Zotero 管理文献，以 Typora 编写日常 Markdown 笔记，以 Obsidian 建立和维护本地知识库，以 ChatGPT 承担解释、梳理、连接和协作辅助的角色，并在需要时结合 Wolfram、LaTeX、Git 与 MCP（Model Context Protocol，模型上下文协议）。

它不是要让某一个软件取代其余工具，也不是一开始就搭建复杂的自动化系统；核心是给不同工具分配清晰职责，使研究材料能从“收集”逐步转化为“自己的理解”，再沉淀为可验证的推导与正式输出。

1. 总体认识：不是工具堆叠，而是研究信息的分层流动
#

这套工作流可以理解为四类研究对象的流动：外部资料、个人理解、计算验证和正式成果。

外部文献与书目资料
        │
        ▼
      Zotero
        │  阅读、标注、筛选、记录出处
        ▼
Typora / Obsidian 中的 Markdown 笔记
        │  形成自己的理解、问题、概念联系与研究计划
        ▼
ChatGPT 协助梳理、解释、比较与生成工作草稿
        │
        ├────────────► Wolfram / Mathematica：符号或数值检验
        │
        ▼
推导记录、已确认结果与 LaTeX 正式文稿
        │
        ▼
      论文、报告、图表或其他成果

其中，ChatGPT 不应被定位为“取代阅读、理解或判断的人”，而应成为研究过程中的智能中间层：帮助从文献中提炼问题，连接分散笔记，检查表达是否自洽，准备可供人审阅的草稿，并在授权范围内调用合适的工具。

2. 各工具的职责边界
#

2.1 Zotero：外部文献资产与可追溯出处
#

Zotero 最适合保存和管理外部来源，而不是承载全部研究思考。它可以负责：

  • 保存 PDF、DOI、作者、期刊、年份和标签等书目信息；
  • 按研究主题、阅读状态或项目对文献分类；
  • 进行高亮、批注和简短阅读备注；
  • 管理引用信息，并按需要导出 BibTeX 等格式；
  • 保留“某个结论来自哪里”的可追溯线索。

例如，阅读一篇关于 AdS/CFT 的论文时，Zotero 中应保存论文原件与元数据，并可留下“需要复核的页码”“值得回看的公式”或初步疑问。这样，当日后写作或核查时，可以返回原文，而非只依赖记忆或二手转述。

但 Zotero 不必承担如下内容的长期管理：

  • 自己对概念之间关系的系统理解；
  • 多篇文献比较后形成的判断；
  • 尚未解决的研究问题；
  • 逐步发展的推导、计算尝试和项目决策。

这些属于个人研究知识，更适合进入 Markdown 笔记与知识库。

2.2 Typora：低摩擦的日常思考与写作入口
#

Typora 可以作为日常编写 Markdown 的主要界面。它的价值不在于“替代知识库”，而在于让记录过程足够顺手：读论文时写阅读笔记、出现想法时写问题、完成一段计算时写推导说明，都不应被复杂的格式或管理步骤打断。

适合用 Typora 写的内容包括：

  • 一篇论文的阅读摘记与个人理解；
  • 某个公式、定义或物理图像的解释；
  • 当天的研究日志；
  • 某次计算或推导的过程记录；
  • 临时问题、待验证猜想和后续行动项；
  • 计划放入论文的段落草稿。

Markdown 文件本身是普通文本文件，因此可以先由 Typora 写作，之后再由 Obsidian 统一管理；两者不是竞争关系。只要文件保存于同一套有组织的目录中，Typora 负责“写”，Obsidian 负责“连接、检索与回看”。

2.3 Obsidian：长期知识库与概念网络
#

Obsidian 适合将 Markdown 文件组织成一个 Vault（知识库），并通过内部链接、标签、搜索和图谱等方式展示知识之间的关联。对理论物理、数学或持续性技术研究而言，许多概念不是线性章节关系，而是网络关系。

例如，Chern–Simons 项可能同时关联拓扑、异常、边界理论、全息、量子霍尔效应和规范场论。将这些主题各自形成笔记并以链接连接，通常比把所有内容塞进一份长文档更便于长期维护。

Obsidian 中更值得保存的是“消化后的知识”，例如：

  • Chern-Simons 项：定义、适用维度、变分要点、常见约定与未解问题；
  • 异常：类型、物理含义、与边界条件或反常流入的关系；
  • Maldacena 1997：论文主旨、关键公式、个人疑问以及与其他概念的连接；
  • 开放问题：当前尚无结论、需要检索、推导或讨论的问题；
  • 项目决策：已确认的度规号差、单位制、符号约定和选择理由。

知识库的目标不是复制所有原文，而是让未来的自己和协作中的 AI 能回答：我为什么相信这个说法？它与什么相连？依据在哪里？下一步还缺什么？

2.4 ChatGPT：推理、整理、连接与协作辅助层
#

ChatGPT 最适合参与“知识转换”，而不是成为未经核验的结论来源。它可协助：

  • 根据已有笔记解释难点、补全逻辑链和比较不同表述；
  • 将多篇文献笔记按问题、方法、结论与分歧进行整理；
  • 把零散记录转为清晰的提纲、研究日志或 Markdown 草稿；
  • 找出概念笔记之间可能缺失的链接；
  • 把确认过的笔记整理为 LaTeX 写作的结构与初稿；
  • 设计计算检查步骤，并在具备相应工具连接时协助调用计算环境；
  • 提醒区分原文事实、个人推断、计算证据和尚待验证的猜想。

对于关键公式、原始文献含义、数值结果和学术引用，最终仍应由研究者回到论文、计算输出或可靠来源完成核验。推荐的路径是：

想法或文献内容
  → Markdown 记录
  → ChatGPT 协助梳理
  → 人工审阅与必要的计算/原文核查
  → 已确认结果
  → 正式论文或报告

2.5 Wolfram / Mathematica、LaTeX 与 Git：验证、输出和版本
#

  • Wolfram / Mathematica：适合符号运算、张量计算、积分、极限、数值实验及对中间推导的交叉检查。计算输入、前提与结果摘要应当保留在项目文件中，使结论可复现。
  • LaTeX：适合论文、报告等正式输出。正式稿只应吸收已确认的内容，避免将尚未检验的尝试直接写入最终文本。
  • Git：适合为研究笔记、推导、代码与 LaTeX 源文件保留版本历史。它不是取代思考的工具，但能帮助回答“这个结论或段落何时、为何发生变化”。

3. 推荐的知识流：Zotero → Markdown → Obsidian → 成果
#

第一步：在 Zotero 中收集、筛选并阅读来源
#

先将论文作为“外部资料”管理。每篇准备深入阅读的论文，至少保留准确书目信息和 PDF；阅读时可使用高亮与批注，但不必追求把全部内容摘录下来。

更有价值的是留下少量高密度线索，例如：

  • 该论文要解决什么问题；
  • 哪个公式、论证或图像值得回看；
  • 它依赖哪些假设或约定；
  • 它与当前项目的关系；
  • 读后产生的疑问。

第二步：建立对应的 Markdown 文献笔记
#

当一篇论文对研究有持续价值时，为它建立一份 Markdown 笔记。笔记不需要复述全文，可采用如下结构：

# 文献：作者 - 年份 - 简短标题

## 书目信息
- Zotero 条目：
- 主题标签：
- 阅读状态：

## 这篇论文回答的问题

## 核心方法与关键结论

## 需要回到原文核对的内容

## 我的理解与疑问

## 与当前项目的关联

## 相关笔记
- [[概念 A]]
- [[概念 B]]

其中“我的理解与疑问”尤其重要。它使文献阅读从收藏行为转化为研究过程，也给后续与 ChatGPT 的讨论提供了清晰上下文。

第三步：在 Obsidian 中将文献笔记连接到概念与问题
#

同一篇文献往往不只属于一个文件夹。除了按主题或项目放置，还可在笔记中通过链接连接概念、推导和问题，例如：

本文对 [[全息异常]] 的讨论可能依赖 [[Chern-Simons 项]] 的边界变分。

待核对：[[开放问题：边界条件如何影响异常项]]

这样，未来从一个概念进入时，可以回溯到相关文献、推导和问题，而不必仅靠记忆翻找文件。

第四步：把需要深入处理的内容转入项目推导区
#

当某个问题从阅读阶段进入实际研究时，应建立单独的推导或计算文件，明确写出：已知前提、符号约定、目标、每一步推导、检查方法、当前状态和待解决问题。

推导文件允许包含失败的尝试与修正记录；正式论文不应承担这一功能。将二者分开，可以保护研究过程的可追溯性，也避免把未经确认的内容误写为结论。

第五步：确认后再进入 LaTeX 正式输出
#

当逻辑、计算和来源已经核对，再把内容转入论文或报告。建议在每次转入前检查：

  • 公式中所有符号是否已经定义；
  • 前提、边界条件和单位制是否一致；
  • 结论是严格推导、计算证据还是推测；
  • 文献出处是否可追溯；
  • 对关键计算是否有可复现记录。

4. 面向研究项目的目录建议
#

不必一开始建立庞杂目录。下面是一套可由 Typora 编写、由 Obsidian 打开管理、并能逐步接入 LaTeX 与计算工具的结构：

Research_Project/
├── README.md                    # 项目目标、范围、现状与导航
├── AGENTS.md                    # AI 协作规则、质量要求和工具约定
├── 00_inbox/                    # 待整理的聊天记录、临时资料、想法
├── 01_literature/               # 文献笔记；Zotero 仍保存 PDF 与书目信息
├── 02_concepts/                 # 概念卡片、定义、关系与背景知识
├── 03_derivations/              # 中间推导、计算记录和检查
├── 04_questions/                # 开放问题、待验证事项、研究计划
├── 05_results/                  # 已确认结论、图表、数据和可复现结果
├── 06_paper/                    # LaTeX 正式文稿及相关资源
└── 07_archive/                  # 历史版本或不再使用的材料

这不是唯一正确的结构。关键分界在于：

原始资料 → 个人笔记与问题 → 中间推导 → 已确认结果 → 正式输出

文件夹编号只是为了让文件浏览器保持稳定顺序；Obsidian 中真正的关联可通过链接建立。

5. README.md 与 AGENTS.md 在该系统中的位置
#

README.md：项目入口与共同上下文
#

README 应主要回答“这个项目是什么、现在走到哪里、资料在哪里”。它既帮助未来的自己回到项目，也帮助新的合作者或 AI 快速建立必要上下文。

可写入：

  • 研究问题和范围；
  • 当前阶段、已完成事项与下一步；
  • 重要材料和关键文献；
  • 目录导航；
  • 重要假设、符号约定或边界条件；
  • 仍待解决的核心问题。

AGENTS.md：AI 协作行为约定
#

AGENTS.md 应主要回答“AI 在此项目中应如何工作”。它可以规定：

  • 所有新符号首次出现时必须定义；
  • 明确标注“原文事实”“推导结论”“数值证据”“个人猜想”；
  • 重要公式应做量纲、符号、极限或数值检验；
  • 中间尝试先放入 03_derivations/，不要直接改正式论文；
  • 修改正式稿前先说明拟议改变；
  • 引用与计算结果应保留可追溯来源和可复现记录。

README 与 AGENTS.md 都不必一开始完美。它们应随研究推进持续更新，记录真正影响后续工作的决定。

6. ChatGPT 的具体使用场景
#

场景一：论文阅读后的针对性讨论
#

不要只要求“总结这篇论文”。先将问题写入文献笔记，例如：

需要理解：
1. 大 N 极限在本文中承担什么作用？
2. 某个边界项为何会出现？
3. 这一论证与当前项目中的 Chern-Simons 修正有什么关系？

再请 ChatGPT 围绕这些问题解释、比较或提出验证路线。这样得到的内容会更贴合研究目标；回答中的关键点仍应回到论文核对。

场景二：发现知识网络缺口
#

当 Obsidian 中已有概念笔记时，可以让 ChatGPT 根据笔记提出可能的连接或缺口，例如：某个“异常”笔记是否应关联“异常流入”“边界条件”或“全息重整化”。这类建议是导航，而不是自动成立的知识；添加前应由研究者判断其物理或数学关系是否准确。

场景三：从笔记到论证结构
#

可将已经核对的文献笔记、推导摘要和结果交给 ChatGPT，要求整理为论文小节的逻辑骨架：研究问题、假设、方法、结果、局限与下一步。随后由研究者审阅、补充引用，并写入 LaTeX。

场景四：推导和计算的交叉检查
#

可让 ChatGPT 帮助将一段手算推导拆解为可检查的子步骤，并在具备相应连接或本地工具时，准备 Wolfram/Mathematica 的验证思路。需要保存的不是一句“已验证”，而是计算的输入、参数约定、输出摘要和解释。

场景五：项目连续性维护
#

在一次工作结束时，可让 ChatGPT 根据当天的笔记生成简短研究日志，列出：完成内容、确认结论、仍不确定的地方、下一步和所需资料。下次开始研究时，先读 README、最近的日志和开放问题，就能显著降低重新进入项目的成本。

7. MCP 在未来架构中的作用
#

MCP 的价值不是让研究自动化失控，而是为已授权的工具与数据提供统一连接方式。未来在实际可用、可信并经过授权的连接条件下，ChatGPT 可通过相应能力协助：

ChatGPT
   │
   ├── 文献与引用管理：检索 Zotero 条目、读取允许访问的资料
   ├── 本地知识库：读取或整理指定的 Markdown 笔记
   ├── 计算环境：调用 Wolfram / Mathematica 进行指定检查
   ├── 项目文件：编辑 Markdown、LaTeX 或代码
   └── 版本管理：查看变更、准备提交说明

是否能够连接某一具体应用，取决于当时平台支持、所安装的连接器、权限范围与本地配置。因而现阶段最优先的工作不是追求“所有工具自动打通”，而是先让文件结构、命名、笔记习惯和项目规范稳定下来。结构清晰后，未来接入工具时才不会把混乱的资料自动化地放大。

8. 分阶段实施建议
#

阶段一：先形成最小可用习惯
#

当前可先稳定使用：

  • Zotero：收集、分类和阅读文献；
  • Typora：随时写 Markdown；
  • 一个固定的本地项目目录：存放笔记、推导和正式材料；
  • README.md：写清研究目标、当前问题与资料位置。

此阶段不需要依赖复杂的插件或自动同步。

阶段二：完成 Obsidian 本地环境并整理 Vault
#

将已有 Markdown 纳入 Obsidian Vault，逐步建立文献笔记、概念笔记、推导和问题之间的链接。先从当前一个真实研究项目开始，而不是试图一次整理全部历史资料。

阶段三：加入项目模板与版本管理
#

为每个中长期项目复制统一模板，包含 README、AGENTS、文献、概念、推导、问题、结果和论文目录。对需要长期维护的项目，可开始使用 Git 保存 Markdown、代码和 LaTeX 源文件的历史。

阶段四：按实际需要接入计算与 MCP
#

当某个重复步骤已被证明稳定、明确且值得自动化时，再考虑连接 Zotero、计算环境、文件系统或其他服务。每次增加连接时都应先明确：它能访问什么、是否可以写入、执行错误如何回滚、哪些操作必须人工确认。

9. 可长期坚持的原则
#

  1. Zotero 保存别人产生的知识。 保留文献原件、书目与出处。
  2. Obsidian 保存自己消化后的知识。 用自己的语言记录理解、关系、问题与决定。
  3. Typora 让思考保持低摩擦。 先把内容写下来，再逐步整理。
  4. ChatGPT 协助知识转换，而不替代核验。 它可以解释、组织和提出检查路线；关键结论仍须回到资料与计算。
  5. 推导区与正式稿分离。 允许探索、修正和失败的中间记录存在，同时保护正式输出的可信度。
  6. 所有重要结论保持可追溯。 能找到原文、笔记、计算输入或明确的推导依据。
  7. 先稳定工作流，再增加自动化。 复杂集成应服务于已经有效的研究习惯。

#

这套环境的核心不是把 Zotero、Typora、Obsidian、ChatGPT、Wolfram 和 LaTeX 简单并列，而是建立一条清晰的研究链：Zotero 管理外部文献，Typora 记录即时思考，Obsidian 组织长期知识网络，ChatGPT 协助连接与整理，计算工具负责检验，LaTeX 承载正式成果。

当每个研究项目都保留目标、约定、文献笔记、问题、推导和已确认结果时，研究过程就不再依赖某次对话或个人短期记忆。未来无论由自己、合作者还是具备适当权限的 AI 接续工作，都能从已有上下文继续，而不是重新开始。
